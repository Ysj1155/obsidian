# 개요

- **OCP-OPF-Testing-and-Validation** 리포지토리는 OCP(Open Compute Project)의 OPF(Open Programmable Framework) 스택을 대상으로 한 검증용 테스트 모음입니다. Pytest 기반으로 수많은 검증 시나리오(부팅 복구, 성능 테스트, 오류 주입, 텔레메트리 수집 등)를 **자동화된 프레임워크**로 제공합니다. 주 목적은 **공급망 전체에서 일관된 테스트 체계**를 마련하여, 장비 제조사별로 제각각인 테스트 코드를 벗어나 **재현성 있는 검증 프로세스**를 구현하는 것입니다. 리포지토리 구조는 Pytest 스위트, HAL(하드웨어 추상화 계층), 텔레메트리 핸들러 등으로 구성되어 있으며, OCP 표준화 형식으로 로그/결과를 출력할 것으로 보입니다.

## 주요 구성 요소 및 아키텍처

- **테스트 아키텍처:** Pytest를 테스트 러너로 사용하며, `conftest.py`나 `fixtures/` 폴더에 공통 초기화 코드(셋업/티어다운)를 둡니다. 테스트 함수는 `tests/` 디렉터리에 모여 있고, 각 테스트는 DUT(Device Under Test)와 통신하기 위해 HAL 인터페이스를 활용합니다.
- **HAL(하드웨어 추상화 계층):** 제조사나 플랫폼 종속 코드를 캡슐화하는 모듈이 별도로 존재합니다. 예를 들어 `hal_vendor_x.py`, `hal_vendor_y.py` 같은 파일에서 NVMe 명령어 실행, 파워 사이클, ECC 오류 주입 같은 구체적 인터페이스를 구현합니다. 이를 통해 동일한 테스트 코드를 여러 하드웨어에서 재사용할 수 있습니다.
- **테스트 구성과 시나리오:** 주로 ①부팅 복구 확인 ②정상/비정상 동작 검증(전원 차단, 펌웨어 업데이트 등) ③성능 측정(읽기/쓰기 벤치마크) ④오류 주입(메모리 에러, 미디어 오류) ⑤신뢰성 테스트(장시간 스트레스) 등이 있습니다. 모든 시나리오에서 로그와 SMART 데이터를 수집해 결과를 확인합니다.
- **에러 주입 메커니즘:** 펌웨어나 소프트웨어 단에서 제어 가능한 방식으로 **미디어 오류(flash bit flips)**, **전원 실패 시뮬레이션**, **커맨드 프로토콜 오류** 등을 인위적으로 발생시켜 ECC 및 재시도 경로를 검증합니다. 예컨대 NVMe 명령 오류나 운전모드를 토글하는 메소드를 사용하며, `hal` 모듈에서 이를 구현합니다.
- **텔레메트리 수집:** NVMe SMART, OCP 표준 로그, 온도/전력/지연 시간 등 다양한 지표를 측정합니다. 예를 들어 SMART의 **Available Spare**, **Media and Data Integrity Errors**, **Power-on Hours** 같은 필드를 조회하고, 운영 중 치명 상태나 경고를 캐치합니다. 시험 중 수집된 데이터는 이후에 비교·분석됩니다.
- **FDP (Flexible Data Placement):** 주로 쓰기 증폭(WAF)을 줄이는 기능으로, 업데이트 빈도나 데이터 특성에 따라 블록 분리 배치를 테스트합니다. 테스트에서는 FDP 지원 여부를 확인하고, FDP를 활성화한 상태에서 WAF가 낮아지는지, GC 오버헤드가 줄어드는지를 점검합니다. 이는 **FDP(쓰기 증폭 최소화)**와 연관된 메트릭(예: WAF, GC 오버헤드)을 비교하여 평가합니다.
- **OCP 통합 및 오픈 생태계:** 테스트 결과는 OCP 진단 포맷(JSON/CSV)으로 저장하고, OCP-OPF 생태계 전반(예: OCP Dashboard, 릴리스 스크립트)과 연동될 것입니다. 또한 스크립트와 YAML 설정은 오픈소스로 공개되어, 타사나 클라우드 벤더도 동일 환경에서 같은 테스트를 돌릴 수 있도록 합니다. 리포지토리에 CI(Continuous Integration) 워크플로우나 Issue/PR을 통해 변화 관리가 이루어지는 것으로 추정됩니다.

> **** 이 리포지토리는 **OPF 스택의 포괄적 검증 체계**를 제공하며, Pytest와 HAL 패턴을 사용해 제조사 독립적인 테스트 자동화를 구현합니다. SSD 검증뿐 아니라 OPF를 구성하는 모든 요소(스토리지, CPU, NIC 등)를 대상으로 할 것으로 보이며, 특히 에러 주입과 텔레메트리 분석에 중점을 둡니다.

## 심층 파일 탐색 권장순위 및 이유

1. **`README.md`** – 프로젝트 전반 소개와 설치/실행 방법 기재. 테스트 스위트 구조 이해의 출발점이므로 최우선 검토 대상.
2. **`docs/` 디렉터리** – 아키텍처, 사용 가이드, 규약 등 문서가 모여 있는 곳. 특히 `architecture.md`, `testing_scenarios.md` 등을 통해 의도된 검증 시나리오를 파악.
3. **`hal/` 폴더** – 벤더별 구체 구현체 확인. 어떤 장치별 메소드(예: `power_cycle()`, `inject_fault()`)가 지원되는지, 일관성 여부를 파악.
4. **`tests/` 폴더** – 실제 Pytest 테스트 코드들. 단위별로 어떤 검증이 이루어지는지, fixture 사용 방식, 의존성 등을 확인.
5. **`conftest.py`** – Pytest 공통 설정(예: DUT 커넥션, 공통 pytest fixtures). 테스트 환경 구성 방식을 파악하는 데 필수.
6. **CI 설정 파일 (`.github/workflows/` 등)** – 테스트 자동화 및 릴리스 프로세스. 어떤 명령어로 빌드/테스트/배포하는지 확인.
7. **`scripts/` 또는 `utils/` 폴더** – 부가적 스크립트(예: 결과 포맷터, 데이터 수집 도구). 문서와 실제 동작 간 차이를 검토.

## 다음 연구 과제 및 우선순위

1. **코드 실행 테스트:** 실제 장비 없이도 시뮬레이션 또는 가상 DUT를 사용해 Pytest 스위트를 실행해 봅니다. 이를 통해 fixture 설정과 HAL 동작을 파악할 수 있습니다.
2. **CI 워크플로우 분석:** GitHub Actions나 Jenkins 설정을 확인하여, 테스트 환경(도커 이미지, 툴체인 버전, 하드웨어 환경 등)을 이해합니다.
3. **이슈/PR 검토:** 사용자 리포지토리의 Issue와 Pull Request에서 현재 알려진 문제점이나 기능 토론을 확인합니다. 특히 SSD 검증 관련으로 누락된 기능이나 업데이트 계획이 있는지 살펴봅니다.
4. **관련 표준 및 문서 조사:** OCP OPF 사양서와 NVMe 2.x 테크니컬 프로포절(FDP 등)을 참조해, 테스트 요구사항과 코드 구현이 표준에 부합하는지 검증합니다.
5. **테스트 재현성 확인:** 다른 하드웨어(예: OCP 지원 SSD)에서 스크립트를 돌려보거나, 결과 로그 포맷(JSON 등)을 확인하여 “Shift-Left” 신념대로 실제 재현이 가능한지 평가합니다.

## 시각화 다이어그램 및 테이블

mermaid

복사

```
flowchart TB
  A[테스트 시작<br/>(Pytest 및 Fixtures 초기화)] --> B[HAL 초기화<br/>(장치 인터페이스 설정)]
  B --> C[장치 설정 및 구성<br/>(DUT 준비, 펌웨어 로드 등)]
  C --> D[검증 시나리오 실행<br/>(전원/부팅, 오류 주입, 성능, 복구 등)]
  D --> E[데이터/로그 수집<br/>(SMART, 텔레메트리, syslog, NVMe 커맨드 결과)]
  E --> F[결과 분석 및 평가<br/>(합격/불합격 판정, 리포트 생성)]
  D --> G[특수 시나리오<br/>(FDP 활성화, 쓰기 증폭 분석)]
  G --> E
```

- **설명:** 좌→우 방향 플로우로, 초기화 단계부터 테스트 시나리오 수행, 데이터 수집, 결과 분석의 순서로 표시했습니다. HAL 계층을 통해 장치 의존성을 추상화하고, 다양한 시나리오(오류 주입, FDP 등)가 실행됩니다.

| **필드/메트릭**               | **카테고리**      | **설명 및 검증 포인트**                                                                      |
| ------------------------ | ------------- | ------------------------------------------------------------------------------------ |
| **Available Spare**      | SMART(예비 공간)  | SSD에 사용 가능한 예비 블록 비율. 예비 공간이 가득 차면 성능 저하와 내구도 위험이 증가함. 정상 복구 시나리오에서 값 감소/증가 모니터링 필요. |
| **Critical Warning**     | SMART(경고 비트)  | 온도 초과, 긴급 정전 등 치명적 상태를 나타내는 플래그. 전원 장애/발열 시나리오에서 적절히 설정되는지 확인.                       |
| **Media Errors**         | SMART(오류 카운트) | NAND 비트 에러, ECC 복구 건수 등. 오류 주입 테스트 후 카운트가 증가해야 하며, ECC 기능 검증.                        |
| **Power Cycle Count**    | Telemetry     | 전원 사이클 누적 횟수. 전원 장애 테스트 후 증분 여부로 실제 리셋 여부를 확인.                                       |
| **Temperature**          | Telemetry     | 장치 온도. 과부하 시나리오에서 상승 추세, 냉각 효과 등을 평가.                                                |
| **FDP WAF**              | FDP 관련        | 쓰기 증폭(Write Amplification Factor). FDP 활성화 시 WAF가 낮아지는지 비교(예: 5→1).                  |
| **GC Count/Duration**    | FDP 관련        | 가비지 컬렉션 실행 횟수 및 소요 시간. FDP로 인해 GC 비용이 줄어드는지 검증.                                      |
| **Throughput (IOPS/BW)** | 성능            | 읽기/쓰기 IOPS 또는 대역폭. 정상 상태와 FDP 적용 시 성능 비교.                                            |
|                          |               |                                                                                      |

- **설명:** 좌측은 측정 항목 이름, 중앙은 종류(예: SMART, Telemetry, FDP 관련), 우측은 해당 항목이 무엇을 의미하는지와 검증 관점을 적었습니다. 예를 들어 _Available Spare_는 예비 블록 비율이고, 이 값이 부족해지지 않도록 예비 블록 동작을 테스트해야 합니다. _FDP WAF_는 호스트 힌트에 따른 쓰기 증폭 정도로, FDP 기능의 핵심 평가 지표입니다.
