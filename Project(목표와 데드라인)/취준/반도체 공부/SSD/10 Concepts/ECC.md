# ECC

DRAM에서 비트 하나를 잘못 읽었다고 하자. 컨트롤러는 원본을 가지고 있지 않은데 **어떻게 오류가 났다는 사실을 알고, 어느 비트를 뒤집어야 하는지 판단할까?** 이 노트에서는 Hamming 코드로 직접 계산한 뒤, 같은 원리가 시스템 DRAM·DDR5 칩 내부·SSD의 NAND에 각각 어떻게 적용되는지 살펴본다. [Hamming의 오류 검출·정정 원 논문](https://doi.org/10.1002/j.1538-7305.1950.tb00463.x)

처음 읽을 때는 1–3절의 **데이터 `1011`** 하나를 끝까지 따라간다. 그다음 4–7절에서 검사 회로의 위치와 어떤 오류가 관찰되는지 연결한다. [[DRAM]] · [[DDR4와 DDR5]]

## 1. 검사 비트가 알려주는 것

원본 데이터에 검사 비트를 붙여 **코드워드(codeword)**를 만든다. 읽을 때 데이터와 검사 비트를 함께 가져와 규칙을 만족하는지 확인한다. 여러 검사 결과를 모아 만든 값이 **syndrome**이다. 코드는 쓸 수 있는 비트열의 범위를 제한한다. 그 덕분에 일부 비트가 달라진 값을 받더라도 해당 코드의 정정 범위 안에서 원래 코드워드를 찾을 수 있다.

짝수 패리티 하나를 예로 들면 `1011`에는 1이 세 개 있어서 검사 비트 `1`을 붙인다. 전체 1의 개수가 짝수가 된다. 비트가 하나 바뀌면 저장된 전체 비트의 XOR가 `1`이 되지만, **어느 자리**가 바뀌었는지 알 수 없다. 두 비트가 바뀌면 다시 짝수여서 이 검사로는 검출되지 않는다.

### Hamming distance와 정정 범위

두 비트열의 **Hamming distance**는 서로 다른 자리의 수다. 예를 들어 `1011`과 `1000`은 두 자리가 다르므로 거리가 2다. 코드 전체에서 가장 가까운 두 유효 코드워드 사이의 거리를 `d_min`이라 한다.

- 유효 여부만 검사하면 최대 `d_min − 1`개의 비트 오류를 검출할 수 있다.
- 가장 가까운 코드워드를 찾는 방식으로 보장할 수 있는 정정 개수는 `floor((d_min − 1) / 2)`다.
- 두 능력을 동시에 평가할 때는 디코더 정책이 중요하다. 거리 3인 Hamming 코드는 1비트 정정이 가능하지만, 정정 모드에서 2비트 오류가 다른 코드워드의 1비트 오류로 보일 수 있다.

거리 3인 코드워드 두 개 `000`과 `111`을 생각해 보자. `000`이 한 비트 바뀐 `001`은 `000`에 더 가깝다. 두 비트가 바뀐 `011`은 오히려 `111`에 가깝다. 정정 범위를 넘으면 잘못된 값을 정상으로 돌려줄 수 있다. 이를 **오정정(miscorrection)**이라고 한다. [Hamming 원 논문](https://zoo.cs.yale.edu/classes/cs323/doc/Hamming.pdf)

## 2. Hamming(7,4)을 손으로 계산하기

데이터 4비트와 짝수 패리티 검사 비트 3개를 사용한다. 자리 번호를 왼쪽부터 1–7로 붙인다. 패리티는 2의 거듭제곱 자리인 1·2·4에 놓고 데이터는 3·5·6·7에 둔다.

| 검사 | 검사하는 자리 | 그룹을 고르는 규칙 |
|---|---|---|
| P1 | 1, 3, 5, 7 | 자리 번호의 이진 표현에서 1의 자리 비트가 1 |
| P2 | 2, 3, 6, 7 | 2의 자리 비트가 1 |
| P4 | 4, 5, 6, 7 | 4의 자리 비트가 1 |

```text
자리:       1   2   3   4   5   6   7
역할:       P1  P2  D1  P4  D2  D3  D4
데이터 배치: ?   ?   1   ?   0   1   1

P1 = D1 XOR D2 XOR D4 = 1 XOR 0 XOR 1 = 0
P2 = D1 XOR D3 XOR D4 = 1 XOR 1 XOR 1 = 1
P4 = D2 XOR D3 XOR D4 = 0 XOR 1 XOR 1 = 0

저장하는 코드워드: 0 1 1 0 0 1 1
```

읽을 때 **6번 자리**가 `1 → 0`으로 바뀌어 `0110001`을 받았다고 하자.

```text
s1 = r1 XOR r3 XOR r5 XOR r7 = 0 XOR 1 XOR 0 XOR 1 = 0
s2 = r2 XOR r3 XOR r6 XOR r7 = 1 XOR 1 XOR 0 XOR 1 = 1
s4 = r4 XOR r5 XOR r6 XOR r7 = 0 XOR 0 XOR 0 XOR 1 = 1

syndrome = (s4 s2 s1)₂ = 110₂ = 6
6번 자리를 반전 → 0110011로 복구 → 3·5·6·7번 자리에서 1011 추출
```

검사 그룹을 이렇게 고르면 각 자리의 조합이 서로 다르다. 6번은 P2와 P4에만 들어 있으므로 6번 하나가 바뀌면 그 두 검사만 실패한다. 이 관계를 행렬로 쓰면 각 검사 그룹이 행 하나를 이루는 패리티 검사 행렬 `H`가 된다. 유효 코드워드 `c`는 `Hc = 0`을 만족한다. 받은 값이 `r = c XOR e`이면 syndrome `Hr = He`이므로 하나의 오류는 해당 자리의 열로 나타난다. 모든 계산은 2를 법으로 한다.

## 3. SECDED는 두 비트 오류를 어떻게 가르는가

위 Hamming(7,4)에 **전체 짝수 패리티** `P0` 하나를 더 붙이면 확장 Hamming(8,4)이 된다. 예시의 앞 7비트에는 1이 네 개 있으므로 `P0 = 0`이다. `s`는 앞 7비트의 syndrome, `q`는 전체 8비트의 XOR로 둔다.

| syndrome `s` | 전체 XOR `q` | 최대 두 비트가 바뀌었다는 가정 아래의 판정 |
|---|---:|---|
| 0 | 0 | 오류 징후가 없다. |
| 0이 아님 | 1 | 앞 7비트 중 하나가 바뀌었다. `s`가 가리키는 자리를 고친다. |
| 0 | 1 | 전체 패리티 `P0`만 바뀌었다. |
| 0이 아님 | 0 | 두 비트 오류를 검출했다. 단일 비트 정정을 수행하지 않는다. |

예로 **3번과 5번**이 함께 바뀌면 `s = 3 XOR 5 = 6`이다. 앞 절에서 6번 하나가 바뀌었을 때와 같은 syndrome이지만, 전체 XOR가 0이므로 두 비트 오류로 판정한다. 이것이 **SECDED(Single Error Correction, Double Error Detection)**가 단일 오류를 고치면서 이중 오류를 구별하는 방법이다.

세 비트부터는 이 표의 보장 범위를 벗어난다. 예를 들어 1·2·3번이 바뀌면 `s = 0`, `q = 1`이 되어 디코더가 `P0` 오류로 해석할 수 있다. 검사 비트 수가 같아도 코드와 디코더의 보호 단위·오류 모델을 확인해야 한다. **두 비트가 서로 다른 코드워드에 한 개씩 들어갔다면**, 각 코드워드의 독립적인 단일 오류로 볼 수 있다. [Hamming 원 논문](https://doi.org/10.1002/j.1538-7305.1950.tb00463.x)

## 4. DRAM과 SSD에서 어디를 보호하는가

| 적용 위치 | 검사하거나 정정하는 지점 | 예시와 범위 |
|---|---|---|
| DDR5 on-die ECC | DRAM 칩 내부의 저장 배열과 내부 디코더 | Micron이 설명한 128 data bits + 8 check bits의 단일 오류 정정. 칩에서 값을 내보내기 전에 동작한다. |
| 시스템 DRAM ECC | 메모리 컨트롤러가 읽은 데이터와 검사 비트 | 컨트롤러가 생성한 검사 비트를 함께 저장하고 읽을 때 검사한다. 코드 선택, 정정 방식, 오류 보고는 플랫폼에 따른다. |
| SSD 내부 데이터 경로 | 보호를 설정한 컨트롤러 SRAM·DRAM·내부 전송 구간 | 데이터·메타데이터 버퍼 등에서 발생하는 손상을 감지하거나 정정할 수 있다. 검사 비트 생성·검사 지점은 제품마다 확인한다. |
| NAND 미디어 ECC | NAND에서 감지한 코드워드를 복호화하는 단계 | 예로 SSD 컨트롤러에서 BCH 또는 LDPC를 디코딩한다. NAND 부품이 내부 ECC를 처리하는 구성도 있다. |

DDR5 칩 내부에서 복호화가 끝난 뒤 보드 배선에서 생긴 오류는 on-die ECC가 다시 검사할 수 있는 위치를 벗어난다. 시스템 ECC가 구성돼 있다면 컨트롤러가 받는 데이터에 대해 독립적으로 검사를 수행할 수 있다. 한편 SSD 내부에서 올바르게 인코딩한 **다른 LBA의 데이터**를 잘못 반환했다면, NAND ECC가 그 코드워드를 정상으로 판정할 수 있다. 이 오류는 주소·데이터 대응 관계까지 검사하는 실험이나 해당 경로의 보호 기능을 통해 다룬다. [Micron DDR5 장치 자료](https://www.micron.com/products/memory/dram-components/ddr5-sdram) · [[Fadu PCIe 3.0 SSD 브로셔]] · [[FTL]]

### 검출, 정정, 재시도, 복구를 분리하기

- **ECC 정정**은 남아 있는 코드워드의 검사 비트로 원래 값을 추정한다.
- **CRC**는 데이터와 검사값이 일치하는지 확인하는 데 사용한다. 일반적인 CRC 검증 경로는 불일치 시 폐기·재시도·에러 처리를 맡긴다.
- **Retry**는 데이터를 다시 읽거나 전송한다. NAND에서는 다른 기준 전압으로 다시 감지하는 방식도 있다.
- **미러·패리티 기반 복구**는 독립적인 복사본이나 다른 조각을 사용한다. ECC 디코더의 정정 범위를 넘어선 경우에도 설계에 따라 복구 경로가 있을 수 있다.
- **Scrub**은 저장된 데이터를 순회 검사하고 필요시 정정된 값을 다시 저장하는 정책의 한 예다. DRAM의 주기적 refresh, DRAM scrub, NAND 데이터 재배치는 목적과 동작이 다르다.

## 5. NAND에서 BCH와 LDPC가 하는 일

NAND는 셀의 문턱전압 구간을 보고 비트를 판독한다. P/E 사이클에 따른 열화, 시간에 따른 retention 변화, 읽기 간섭은 전압 분포나 감지 결과에 영향을 줄 수 있다. 읽은 비트가 일부 틀려도 복호화할 수 있게 데이터와 검사 비트를 코드워드로 저장한다. 코드워드 크기와 배치는 제품 설계에 따르며 하나의 NAND 페이지에 코드워드가 여러 개 들어갈 수 있다. [Cai 외의 MLC NAND retention 실험](https://arxiv.org/abs/1805.02819) · [Cai 외의 MLC NAND read disturb 실험](https://arxiv.org/abs/1805.03283)

- **BCH**는 정해진 코드워드 내에서 일정 수의 비트 오류를 정정하도록 설계할 수 있는 블록 코드다. 예를 들어 데이터시트의 `정정 능력 t bits / 데이터 구간`을 읽을 때는 어떤 구간의 오류를 세는지 함께 확인한다.
- **LDPC**는 각 검사가 비교적 적은 수의 비트에 연결된 패리티 검사 행렬을 사용한다. 반복 디코더는 만족해야 할 검사와 각 비트의 추정을 서로 갱신해 코드워드를 찾는다. 정정 성공률은 코드, 감지 품질, 반복 횟수 제한, 오류 분포에 영향을 받는다.
- **Hard decision**은 각 비트를 우선 0 또는 1로 판정해 디코더에 넘긴다. **Soft information**은 그 판정이 얼마나 확실한지도 제공한다. NAND를 기준 전압을 바꿔 다시 읽으면 경계에 가까운 셀과 멀리 떨어진 셀을 더 잘 구분할 수 있다. [Cai 외, SSD의 오류 특성 및 복구](https://arxiv.org/abs/1706.08642)

학습용 읽기 경로는 `기본 감지 → 복호화 → 필요시 추가 감지·반복 복호화 → 제품별 복구 또는 실패 보고`다. 빠른 경로에서는 첫 감지와 복호화로 끝난다. 일부 요청에만 추가 감지가 들어가면 평균과 tail이 다르게 움직일 수 있다. fio p99만으로 그 원인을 특정하려면 재시도·복호화 통계가 추가로 필요하다. [[p99 latency]]

### 오류율의 분모 확인하기

| 지표 | 확인할 분자와 분모 |
|---|---|
| RBER (raw bit error rate) | ECC 정정 전 잘못 읽은 비트 수 ÷ 관찰한 raw bit 수. Raw 데이터와 기준값을 확인할 수 있는 시험이 필요하다. |
| UBER (uncorrectable bit error rate) | 정정 및 복구 이후 남는 오류를 읽은 비트 수에 대해 표현한 지표. SSD 사양의 오류 사건 집계 방식과 시험 조건을 확인한다. |
| NVMe SMART의 Media and Data Integrity Errors | 컨트롤러가 감지한 복구되지 않은 데이터 무결성 오류의 발생 횟수. 정정한 raw bit 개수나 NAND RBER을 직접 보여주지 않는다. |

SMART의 해당 값이 0이라면 로그가 집계하는 복구되지 않은 오류가 0건이었다고 해석한다. 정상적으로 교정된 오류나 read-retry가 있었는지를 보려면 장치가 별도 통계를 공개하는지 확인한다. [NVM Express Base Specification 1.4c의 SMART 필드 정의](https://nvmexpress.org/wp-content/uploads/NVM-Express-1_4c-2021.03.09-Ratified-3.pdf) · [[NVMe SMART Telemetry]]

## 6. 검증 실험으로 연결하기

먼저 보호하려는 구간과 기대 결과를 기록한다. 장치 없이도 소프트웨어 코드워드나 HDL 테스트벤치에서 오류 패턴에 대한 기대 동작을 검증할 수 있다. 실제 SSD 내부를 평가하려면 해당 구간에 대한 제어와 관찰 수단이 추가로 필요하다.

| 실험 | 입력 또는 주입 지점 | 확인할 결과 |
|---|---|---|
| 정상 입력 | Encode한 코드워드를 그대로 Decode | 원본 일치, 오류 플래그 없음 |
| 단일 오류 | 8자리 각각을 한 번씩 반전 | 원본 일치, 정정 상태 표시, 검사 비트 자리도 포함 |
| 이중 오류 | 서로 다른 두 자리의 모든 조합 | 이중 오류가 보고되고 정정된 데이터로 취급되지 않음 |
| 범위 밖 오류 | 3비트 반전 등 | 모델의 보장 범위를 문서화하고 오정정이나 미검출 사례를 구분 |
| 주소 불일치 | 다른 주소의 정상 코드워드를 반환하는 모델 | 코드워드 검사는 통과할 수 있고, 주소별 예상 데이터 비교에서 오류를 발견 |

실험에서 중요한 불변식은 **정정 가능하다고 보고한 데이터가 기대값과 일치해야 하고, 정정 불가능하다고 판단한 데이터는 정상으로 완료하면 안 된다**는 것이다. 발생 위치·코드워드 경계·원본과 실제값·상태 표시를 함께 남긴다.

[[External SSD Data Integrity]]의 CRC32C write/readback은 **해당 실행의 파일 데이터가 쓰기 전 기준과 일치했는지** 보는 시험이다. 그 결과에 장치 내부의 정정 횟수나 이중 오류 처리 능력까지 포함시키려면 별도의 내부 관찰과 오류 주입 결과가 있어야 한다. [[FTL Metadata Recovery and Bad Block Handling]]에 있는 모델의 복구 실험도 실제 NAND 복호화가 포함되는지 먼저 확인한다.

## 7. 노트를 닫고 풀기

1. Hamming 예제에서 5번 하나를 반전하면 어느 검사들이 실패하는가?
2. 확장 코드에서 3번과 5번을 함께 반전하면 syndrome과 전체 XOR가 각각 얼마인가? 판정은?
3. 두 코드워드에 비트 오류가 하나씩 있다면 SECDED는 어떤 단위로 판단하는가?
4. DDR5 on-die ECC와 시스템 ECC를 데이터 경로에 표시하고, 칩 밖에서 생긴 오류를 어느 쪽에서 관찰할 수 있는지 설명하라.
5. NAND read-retry가 일부 요청에서만 일어난다면 지연 시간 분포에서 어떤 변화를 의심할 수 있는가? 추가 근거는 무엇인가?
6. NVMe SMART의 Media and Data Integrity Errors가 0이고 CRC32C readback이 성공했다. 이때 확인된 결과와 아직 확인이 필요한 항목을 각각 적어라.

> [!answer]- 확인용 해설
> 1. 5는 이진수 101이다. P1·P4가 실패하고 P2가 통과하므로 syndrome은 5다.
> 2. `3 XOR 5 = 6`, 전체 XOR는 0이다. 두 비트 오류가 검출되며 단일 비트 정정을 하지 않는다.
> 3. 코드워드별로 검사한다. 각각 한 비트만 바뀌었으므로 각 코드워드의 단일 오류로 정정할 수 있다.
> 4. On-die ECC 검사는 칩에서 출력하기 전에 끝난다. 그 뒤 발생한 오류는 경로를 보호하는 시스템 ECC가 구성돼 있을 때 해당 코드 범위에서 관찰할 수 있다.
> 5. 추가 감지와 복호화가 필요한 요청이 느려져 tail이 길어질 수 있다. 빈도가 p99 또는 p99.9에 드러나는지는 분포를 봐야 한다. 재시도 카운터나 시간 정렬된 내부 trace로 검토한다.
> 6. 로그가 집계한 미복구 무결성 오류는 0건이고, 시험한 파일의 readback은 기대 CRC와 일치했다. 정정된 오류 수, 실제 ECC 코드와 보호 범위, 검증하지 않은 조건의 판정에는 다른 증거가 필요하다.

복습할 때는 AI에 완성 답안을 먼저 요청하기보다, 자신이 계산한 syndrome과 판정을 보여주고 **오류 위치나 개수에 대한 전제 하나를 바꿔서 질문해 달라**고 요청한다.
